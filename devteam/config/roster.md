# 부서원 로스터 (Agent Memory)

> **이 파일이 `dev-activity-monitor` 에이전트의 대상 정의이자 장기 기억이다.**
> 부서원의 GitHub ID를 여기에 기록하면 매 회차 이 명단만 조회한다.
> 사람이 직접 손으로 고쳐도 되고, 에이전트에게 "누구 추가해줘"라고 말해도 된다.
> 에이전트 정의 파일(`.claude/agents/dev-activity-monitor.md`)은 건드리지 말 것.

**최종 갱신**: 2026-07-31 (초기 4명 등록)

## §0 조회 설정

| 항목 | 값 | 설명 |
|---|---|---|
| `host` | `github.com` | 사내 GitHub Enterprise를 보려면 여기를 사내 호스트명으로 바꾼다 |
| `default_window` | `30d` | 기본 조회 기간. 특정 월은 `--month 2026-07` 인자로 지정 |
| `include_private_repos` | `true` | 토큰 권한이 허용하는 범위에서 비공개 레포 기여도 집계 |
| `org_filter` | (미설정) | 특정 조직 활동만 볼 경우 `org:이름` 형식으로. 비우면 전체 |

> **중요**: `host`가 `github.com`이면 보이는 것은 **각자의 오픈소스/공개 활동**이다.
> 사내 코드가 GitHub Enterprise에 있다면 `host`를 사내 호스트로 바꾸고
> `! gh auth login --hostname <사내호스트>` 로 로그인해야 사내 활동이 집계된다.
>
> 현재 명단 4명은 모두 **공개 오픈소스 활동이 상당한 계정으로 보인다.** 이 경우 `github.com`
> 조회만으로도 실질적인 작업 파악이 가능하다. 다만 사내 전용 코드는 여전히 조회 범위 밖이다.

## §1 부서원 명단

**기입 형식**: GitHub ID는 프로필 URL(`github.com/여기부분`)의 그 문자열이다. `@`를 붙이지 않는다.
`담당 영역`은 에이전트가 "실제 작업이 담당과 맞는지" 대조하는 데 쓰므로 구체적으로 쓴다.

| GitHub ID | 표시 이름 | 팀 | 역할 | 담당 영역 | 비고 |
|---|---|---|---|---|---|
| `myungjoo` | MyungJoo Ham | (확인 필요) | (확인 필요) | (확인 필요) | 2026-07-31 등록 |
| `leemgs` | Geunsik Lim | (확인 필요) | (확인 필요) | (확인 필요) | 2026-07-31 등록 |
| `again4you` | Sangjung Woo | (확인 필요) | (확인 필요) | (확인 필요) | 2026-07-31 등록 |
| `jaeyun-jung` | (미공개) | (확인 필요) | (확인 필요) | (확인 필요) | 2026-07-31 등록 |

### `(확인 필요)` 칸 채우는 방법

**GitHub ID 4개는 확정 상태이므로 이 로스터로 지금 바로 실행할 수 있다.** 나머지 칸은
채워지면 리포트 품질이 올라가지만 없어도 동작한다.

| 칸 | 누가 채우는가 |
|---|---|
| **표시 이름** | 에이전트가 첫 인증 실행 시 GitHub API의 `user.name` 값으로 자동 기입한다. API에 이름이 없으면 `(미공개)`로 두고 사람이 채운다 |
| **팀 · 역할 · 담당 영역** | **사람이 채운다.** 조직 정보는 GitHub에 없다. 이 칸이 비어 있으면 에이전트는 "담당 영역과 실제 작업의 정렬 점검"(STEP 3-4)과 역할별 해석 보정을 건너뛰고, 리포트에 `역할 정보 없음 - 지표를 역할 맥락 없이 읽고 있음`을 명시한다 |

역할 칸이 비어 있을 때 지표를 그대로 읽으면 오진 위험이 크다. Staff 엔지니어의 낮은 커밋 수는
정상인데 이를 모르면 "활동 저조"로 나온다. 되도록 채우는 것이 좋다.

### 역할별 해석 힌트 (에이전트가 참고)

역할이 다르면 같은 숫자가 다른 의미다. 에이전트는 아래를 감안해 해석한다.

| 역할 | 기대되는 활동 패턴 |
|---|---|
| Staff / Principal | 커밋 수는 낮고 **리뷰 수와 설계 논의(이슈)가 높은** 것이 정상 |
| Senior | 커밋·PR·리뷰가 균형. 리뷰 0건이면 점검 대상 |
| Engineer | PR 생성·머지 중심. 리뷰는 낮을 수 있음 |
| Intern / 신입 | 활동량보다 **머지율과 사이클 타임 개선 추이**를 본다 |
| Maintainer (오픈소스 프로젝트 관리) | 리뷰·이슈 트리아지·릴리즈 작업이 산출의 대부분. 커밋 수로 판단하면 안 된다 |

## §2 제외 대상

아래 계정은 집계에서 제외한다.

| GitHub ID | 이유 |
|---|---|
| `dependabot[bot]` | 봇 |
| `github-actions[bot]` | 봇 |
| `renovate[bot]` | 봇 |

퇴사·전출자는 이 표로 옮기고 `이유`에 `YYYY-MM 전출`을 적는다.
**§1에서 삭제하지 말고 여기로 옮긴다** - 과거 스냅샷의 이름 해석이 깨지지 않게 하기 위함이다.

## §3 감시 레포 (선택)

특정 레포의 활동을 우선해 보고 싶으면 여기에 적는다. 비워두면 각자의 전체 활동을 본다.

| 레포 | 왜 중요한가 |
|---|---|
| (미설정) | |

> 첫 실행 후 에이전트가 관측한 **상위 활동 레포를 여기에 제안**한다. 그중 임원 관심 영역
> (On-Device LLM · Runtime · Compiler · 경량화)과 직결되는 것을 골라 남기면 이후 회차의
> 초점이 잡힌다.

## §4 정체(stalled) 판정 기준

| 항목 | 값 |
|---|---|
| 정체 판정 일수 | `14일` - PR·브랜치가 이 기간 무진전이면 정체 |
| 과부하 판정 | 주말 활동 비중 `30%` 초과 |
| 활동 급감 판정 | 전월 대비 `50%` 이상 감소 |
| 추이 화살표 임계 | `±25%` - 이 미만은 `↔`(노이즈로 간주) |

## §5 운영 메모

지표 변동을 설명하는 사건들. 이것이 없으면 정상적인 감소를 문제로 오진한다.)
