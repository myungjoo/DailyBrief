# 프롬프트 → 에이전트 변환

붙여넣은 원문 프롬프트를 **그대로 파일에 복사하지 않는다.** 원문의 의도를 유지한 채, 반복 실행
가능한 에이전트 규격으로 재구성한다. 원문은 요구사항 명세이고, 산출물은 실행 절차다.

## STEP 0 - 규약 확인

1. `CLAUDE.md` 를 읽어 디렉터리·공통 원칙을 확인한다.
2. `.claude/agents/TEAM.md` 로스터를 읽어 이름 충돌과 역할 중복을 확인한다.
3. 기존 에이전트 중 가장 성격이 비슷한 것 하나를 골라 `.claude/agents/` 에서 읽는다.
   **그 파일의 구조·톤·상세도가 이번 산출물의 기준선이다.** (초기 기준: `ondevice-llm-monitor.md`)

## STEP 1 - 프롬프트 해부

원문에서 아래를 추출한다. 명시되지 않은 항목은 추론하되, 추론했다는 사실을 기억해 둔다.

| 항목 | 질문 |
|---|---|
| 역할 | 누구로서 일하는가. 어떤 전문성을 가정하는가 |
| 트리거 | 언제 호출되는가. 정기 실행인가, 사용자 요청 시인가, 둘 다인가 |
| 입력 | 무엇을 읽어야 하는가. 설정 파일·감시 대상·사용자 인자 |
| 절차 | 어떤 순서로 일하는가. 병렬 가능한 구간은 어디인가 |
| 판단 기준 | 무엇을 중요하다고 보는가. 무엇을 버리는가. 점수/등급 체계가 필요한가 |
| 산출물 | 형식(마크다운/HTML/터미널 요약), 저장 위치, 길이 |
| 상태 | 실행 간에 기억해야 할 것이 있는가 (중복 제거, 이력, 추이) |
| 금지사항 | 하지 말아야 할 것. 원문에 있는 "~하지 말 것" 을 모두 살린다 |

**중복 제거가 필요한지 반드시 판정한다.** 같은 대상을 주기적으로 훑는 에이전트라면 상태 파일 없이는
매번 같은 것을 보고한다. 원문에 언급이 없어도 모니터링형이면 상태 설계를 제안에 포함한다.

## STEP 2 - 확인 (조건부)

다음 중 하나라도 해당하면 `AskUserQuestion` 으로 묻는다. 그 외에는 묻지 말고 진행한다.

- 실행 주기가 불명확한데 정기 실행이 필요해 보임 (매일/주간/수동 전용)
- 산출물 형태가 둘 이상 가능 (터미널 요약만 / 파일 리포트 / Artifact 대시보드)
- 외부 연동이 필요해 보이나 인증 여부가 불명확 (Gmail, Slack, Notion 등 MCP)
- 기존 에이전트와 역할이 겹쳐 통합/신규 판단이 필요

## STEP 3 - 에이전트 정의 작성

`.claude/agents/<name>.md` 를 만든다.

### frontmatter

```yaml
---
name: <케밥케이스. TEAM.md 명명 규칙 준수>
description: <무엇을 하는지 + 언제 호출되는지. 한국어. 트리거 문구를 실제 사용자 표현으로 포함.
             메인 에이전트가 이 한 줄만 보고 호출을 결정하므로 역할 경계를 분명히 쓴다>
tools: <실제 필요한 것만. 아래 표 참조>
model: <opus | sonnet | haiku>
---
```

도구 선택 기준:

| 작업 성격 | tools |
|---|---|
| 외부 정보 수집 | `WebSearch, WebFetch` |
| 파일 읽고 쓰기 | `Read, Write, Edit, Glob, Grep` |
| 웹 대시보드 발행 | `Artifact` |
| 다른 스킬 호출 | `Skill` |
| 셸/스크립트 실행 | `Bash` 또는 `PowerShell` (Windows 환경 - PowerShell 우선) |

모델 선택: 판단·종합·글쓰기 품질이 산출물의 본질이면 `opus`. 정형 추출·분류·집계 위주면 `sonnet`.

### 본문 구조

```markdown
당신은 **<역할>** 이다. <담당 임원의 관심사와 이 에이전트가 존재하는 이유 2~3줄>
<산출물이 어떻게 쓰이는지 한 줄 — 품질 기준이 된다>

## 경로 상수
<작업 공간 파일들을 상수로 선언. 프로젝트 루트는 현재 작업 디렉터리>
<상태 파일이 있으면 "절대 초기화하지 말 것" 을 명시>

---

## 실행 절차

### STEP 0 - 상태 로드
### STEP 1 - 수집/입력
### STEP 2 ~ N - <도메인 로직>
### STEP N+1 - 산출물 작성
### STEP N+2 - 상태 갱신
### 마지막 STEP - 사용자에게 반환할 요약

## 판단 기준
<무엇을 중요하다고 볼지. 점수 체계가 있으면 배점표>

## 금지사항
<원문의 제약 + 팀 공통 원칙에서 유도되는 것>
```

작성 규칙:
- **각 STEP 은 검증 가능하게** 쓴다. "잘 분석한다" 가 아니라 "원문을 열어 수치 X·Y·Z 를 뽑는다".
- **상태 파일은 JSON 스키마를 예시와 함께** 본문에 박아 넣는다. 스키마가 없으면 실행마다 형식이 흔들린다.
- **병렬 가능한 수집은 명시적으로** "한 번에 여러 개 던진다" 고 지시한다.
- 마지막 STEP 에서 반환할 요약 형식을 고정한다. 리포트 전문을 터미널에 다시 쏟지 않도록 금지한다.
- 원문에 있던 표현 중 임원의 도메인 어휘(제품명, 기술 트랙, 벤더명)는 **그대로 보존**한다.

## STEP 4 - 작업 공간 생성

에이전트가 파일을 읽거나 쓴다면 디렉터리와 초기 파일을 만든다.

- `<domain>/config/` - 감시 대상·판단 기준처럼 **사용자가 나중에 손으로 고칠 설정**을 분리해 둔다.
  에이전트 정의에 하드코딩하지 말 것. 설정 변경 때마다 에이전트를 수정하게 된다.
- `<domain>/state/` - 상태 파일을 유효한 빈 초기값으로 생성 (`{"last_run": null, "items": []}` 등).
  파일이 없어서 첫 실행이 깨지는 일을 막는다.
- `<domain>/reports/`, `<domain>/artifact/` - 필요시 `.gitkeep` 대신 디렉터리만 생성.

## STEP 5 - 수동 호출 스킬 (조건부)

정기 실행 에이전트이거나 사용자가 직접 부를 일이 있으면 `.claude/skills/<short-name>/SKILL.md` 를 만든다.
`ondevice-brief` 스킬이 기준 템플릿이다. 반드시 포함할 것:

1. `Agent` 도구로 `subagent_type: "<name>"` 호출, `run_in_background: false`
2. 에이전트에 넘길 프롬프트 본문 (STEP 전체 수행 + 상태 규칙 적용 명시 + `{추가 지시사항}` 자리)
3. **인자 처리 표** - 사용자가 넘길 만한 인자와 해석. 최소 3개 이상 설계
4. 완료 후 반환 형식

## STEP 6 - 정기 실행 등록 (조건부)

매일/매주 자동 실행이 필요하면 `schedule` 스킬로 등록하겠다고 **제안만** 하고, 사용자 승인 후 실행한다.
승인 없이 크론을 만들지 않는다.

## STEP 7 - 등록 및 보고

1. `.claude/agents/TEAM.md` 의 "현재 팀" 표에 행을 추가한다.
2. 사용자에게 아래를 보고한다:
   - 만든 파일 경로 목록
   - 호출 방법 (자동 트리거 조건 / 슬래시 커맨드)
   - **원문에 없어서 내가 결정한 사항** 목록 — 여기가 사용자가 검토해야 할 지점이다
   - 첫 실행을 지금 해볼지 제안

## 금지사항

- 원문 프롬프트를 그대로 붙여넣은 파일을 만들지 않는다. 반드시 절차로 재구성한다.
- 원문의 제약·금지사항을 누락하지 않는다. 하나라도 빠지면 사용자가 신뢰를 잃는다.
- 기존 에이전트 파일을 이번 작업의 부수 효과로 수정하지 않는다 (`TEAM.md` 등록은 예외).
- `tools: *` 로 뭉뚱그리지 않는다.
- 상태 파일이 필요한 모니터링형인데 상태 설계 없이 만들지 않는다.
